01

¿Qué es Claude Code?

Claude Code es una herramienta de coding agéntico disponible en múltiples entornos: terminal, extensión de VS Code, extensión de JetBrains, aplicación de escritorio y navegador web. No es un plugin de autocompletado ni un copilot inline: es un agente que lee tu codebase, ejecuta comandos, edita archivos, interactúa con git y orquesta tareas complejas de forma autónoma.

Arquitectura y modelo mental

Para mí es equivalente a un desarrollador junior extremadamente rápido sentado al lado, en la terminal. Tiene acceso a:

  • Tu filesystem — lee y escribe archivos del proyecto.
  • Bash — ejecuta comandos, corre tests, instala dependencias (con una capa de *sandbox* opcional, ver más abajo).
  • Git — crea branches, hace commits, maneja PRs.
  • Herramientas externas vía MCP — se conecta a APIs, bases de datos y servicios.

El flujo básico es: describís una tarea en lenguaje natural → Claude Code analiza el contexto → planifica → ejecuta pasos (editar archivos, correr tests, etc.) → te muestra el resultado y pide confirmación cuando corresponde.

Concepto clave: Claude Code no "genera código y te lo muestra". Opera sobre tu proyecto real, en tu filesystem real, con tu git real. Es agéntico: toma decisiones, ejecuta acciones y se auto-corrige.

02

Instalación y Setup Inicial

Métodos de instalación

La forma recomendada de instalar ya no es npm (quedó deprecada). Se usa el instalador nativo, que trae su propio runtime y no requiere Node.js:

# macOS / Linux (recomendado)
curl -fsSL https://claude.ai/install.sh | bash

# Homebrew (macOS / Linux)
brew install --cask claude-code

# Windows (recomendado)
irm https://claude.ai/install.ps1 | iex

# WinGet (Windows)
winget install Anthropic.ClaudeCode

# npm (DEPRECADO — requiere Node.js >= 22)
npm install -g @anthropic-ai/claude-code

# Verificar
claude --version

Después: navegás a tu proyecto y ejecutás claude.

Aislamiento — buena práctica, no obstáculo: Para trabajo sensible conviene aislar lo que el agente puede tocar. Tenés dos caminos complementarios: correr Claude Code dentro de un contenedor (Docker, Dev Container, Podman) para reproducibilidad total, o usar el sandbox integrado de Claude Code, que confina los comandos Bash a nivel de filesystem y red sin salir de tu equipo. Elegí según cuánto control necesites.

Directorio de configuración

Por defecto, Claude Code guarda su configuración de usuario en ~/.claude/. Si preferís seguir el *XDG Base Directory Specification* (mantener la config bajo ~/.config en vez de un directorio oculto en el home), podés reubicarla con la variable de entorno CLAUDE_CONFIG_DIR:

# Reubicar la config siguiendo XDG (opcional)
export CLAUDE_CONFIG_DIR="$HOME/.config/claude"

Persistencia en contenedores: Si corrés Claude Code en un contenedor, montá el directorio de config del host para que la autenticación y las preferencias persistan entre ejecuciones.

Autenticación

Claude Code soporta varias formas de autenticación:

  • Login interactivo: ejecutás claude y seguís el flujo OAuth en el browser.
  • API key directa: seteás ANTHROPIC_API_KEY como variable de entorno.
  • Planes de suscripción: usuarios con Claude Pro, Team o Enterprise se autentican con su cuenta de claude.ai.
03

Configuración

Settings y archivos de configuración

Claude Code maneja configuración en múltiples niveles. El comando /config dentro de la sesión permite ajustarla; también existe configuración por archivos:

Alcance Ubicación Uso
Global (usuario)~/.claude/settings.jsonPreferencias personales, aplican a todos tus proyectos
Proyecto (compartido).claude/settings.json en la raízSe commitea — configuración del equipo
Proyecto (local).claude/settings.local.jsonOverrides locales, va a .gitignore

Ejemplo de settings.json de proyecto

{
  "permissions": {
    "allow": ["Read", "Edit", "Bash(npm run *)", "Bash(npx jest *)"],
    "deny":  ["Bash(rm -rf *)", "Bash(git push *)"]
  },
  "env": { "NODE_ENV": "development" }
}

Reglas de permisos (allow / ask / deny)

En settings.json definís qué puede usar Claude sin preguntar, qué requiere confirmación y qué está prohibido:

{
  "permissions": {
    "allow": ["Bash(npm run *)", "Bash(npx jest *)", "Read", "Edit"],
    "ask":   ["Bash(git push *)"],
    "deny":  ["Bash(rm -rf *)", "Bash(git push --force *)"]
  }
}

La sintaxis acepta el nombre de la herramienta sola (Read) o con un patrón de argumento (Bash(npm run *)). El orden de evaluación es deny → ask → allow: la primera regla que coincide gana.

Buena práctica para equipos: Commiteá .claude/settings.json con los permisos del equipo; cada dev agrega sus overrides en .claude/settings.local.json (gitignored). Nunca pongas credenciales en el settings.json compartido — usá settings.local.json o variables de entorno.

Modos de permisos

Más allá de las reglas individuales, Claude Code tiene modos globales que definen el nivel de autonomía de toda la sesión. Se cambian con Shift+Tab en la CLI, o se fijan como default en el settings.json:

Modo Qué puede hacer sin preguntar Cuándo usarlo
defaultLeer archivosTrabajo sensible, primera sesión en un proyecto nuevo
acceptEditsLeer y editar archivosIteración activa en código que estás revisando en paralelo
planSolo lectura — investiga y propone, no ejecuta cambiosExplorar un codebase, planificar una refactorización antes de aprobar
autoTodas las acciones; un clasificador evalúa cada una en segundo planoTareas largas con mínimas interrupciones (requiere Team/Enterprise/API)
bypassPermissionsTodas las acciones sin verificaciónSolo en entornos aislados (contenedores, VMs) — nunca en tu máquina de trabajo

Fijar un modo por defecto en el proyecto, o arrancar en uno específico:

// .claude/settings.json
{ "permissions": { "defaultMode": "acceptEdits" } }
claude --permission-mode plan

Modo auto: Antes de cada acción, un clasificador separado evalúa si es consistente con lo que pediste y bloquea lo que escala fuera del scope (un deploy no solicitado, un push force a main). En planes API/Enterprise el clasificador corre del lado del servidor y no cobra su overhead. Los bloqueos son configurables por el administrador del equipo.

04

Uso Diario y Workflows

Prompting efectivo

Con Claude Code, la calidad del output depende de cómo estructurás el pedido: estás dirigiendo a un agente que va a tomar acciones reales.

  • Sé específico sobre el alcance: "Refactorizá el servicio de autenticación para usar JWT en vez de sesiones" es mejor que "mejorá la autenticación".
  • Indicá restricciones: "No modifiques los tests existentes", "Usá el patrón repository que ya tenemos", "No instales dependencias nuevas".
  • Pedí un plan antes de ejecutar en tareas complejas.
  • Iterá: Claude Code mantiene contexto en la sesión; pedí ajustes sucesivos.
  • Usá referencias concretas: "Mirá cómo lo hacemos en src/services/UserService.py y seguí el mismo patrón".
❌ Prompt débil

Agregá tests al proyecto.

✅ Prompt fuerte

Agregá unit tests para src/services/payment_service.py. Usá pytest con el patrón que ya tenemos en tests/services/. Cubrí pago exitoso, tarjeta rechazada y timeout de la API. Corré los tests al final para verificar que pasen.

Tareas comunes del día a día

Tarea Prompt ejemplo
Explorar codebase nuevo"Analizá la estructura y explicame la arquitectura general y los patrones de diseño que detectes"
Implementar feature"Implementá un endpoint POST /api/users/invite que envíe un email de invitación. Seguí el patrón de los controllers existentes. Incluí validación y tests"
Fix de bug"El test pytest -k 'payment_timeout' falla. Investigá por qué y arreglalo"
Refactoring"Extraé la lógica de validación de order_controller.py a un módulo order_validator.py. Mantené los tests pasando"
Code review"Revisá los cambios del branch feature/payments vs main: bugs, performance y violaciones de patrones"
Migración"Migrá los imports de lodash a imports individuales para reducir el bundle size"

Plan mode — analizá antes de editar

El plan mode hace que Claude investigue el codebase y proponga un plan sin ejecutar ninguna edición. Puede leer archivos y correr comandos de exploración, pero no toca el código hasta que aprobás. Ideal antes de tareas que afectan muchos archivos, o cuando querés entender el impacto antes de comprometerte.

# Modo plan para toda la sesión
claude --permission-mode plan

# Durante la sesión: Shift+Tab hasta llegar a "plan"

Cuando termina de investigar, presenta el plan y te pide cómo proceder: aprobar y continuar automático, aprobar revisando cada edición, o seguir refinando.

Cuándo más útil: Features que tocan más de 5 archivos, migraciones, refactorings que cruzan módulos, o cualquier tarea donde el costo de un error es alto. El plan mode no ejecuta acciones billables hasta que aprobás.

Integración con Git

Claude Code puede crear commits con mensajes descriptivos, manejar branches, crear PRs con título y descripción, y resolver conflictos.

Recordá: Claude Code ejecuta comandos git en tu sesión, como si los tipearas vos. No tiene un conector especial — hereda tu SSH key, tus credenciales, tu .gitconfig y tu usuario. Los commits aparecen con tu nombre. Si vos podés hacer git push desde esa terminal, Claude también.

> Commiteá los cambios con un mensaje descriptivo siguiendo Conventional Commits

> Creá un PR contra main con los cambios de este branch.
  Incluí un resumen y testing instructions.
05

CLAUDE.md en Profundidad

El archivo CLAUDE.md es probablemente la herramienta más impactante para mejorar la calidad de los resultados. Es tu oportunidad de codificar el conocimiento tribal del proyecto: el equivalente a un onboarding document para un dev nuevo, pero escrito para una IA.

AGENTS.md: Si el proyecto no tiene CLAUDE.md pero sí un AGENTS.md (el formato abierto que comparten varias herramientas de coding agéntico), Claude Code lo lee en su lugar. Podés elegir cuál usar desde "Project instructions" en /config. Práctico si ya mantenés un AGENTS.md para otras herramientas.

Anatomía de un CLAUDE.md efectivo

Un buen CLAUDE.md responde las preguntas que un senior nuevo haría en su primera semana:

1. Comandos de build, test y lint

Sin esta sección, Claude adivina y prueba por ensayo y error. Con ella, va directo al comando correcto la primera vez.

# Comandos
- Build: `make build`
- Test (todos): `pytest`
- Test (individual): `pytest path/to/test.py -k nombre`
- Lint: `ruff check .`
- Type check: `mypy src/`

2. Arquitectura y estructura

# Arquitectura
Monorepo con dos servicios principales:
- `services/api` — Backend FastAPI, arquitectura hexagonal
- `services/vision` — Servicio de computer vision (OpenCV + modelos locales)
La comunicación entre servicios es vía cola de mensajes.

3. Convenciones y estilo

# Convenciones
- Nombres de archivos: snake_case; clases: PascalCase
- Imports: absolutos desde la raíz del package, nunca relativos entre módulos
- Error handling: usar el AppError propio, nunca `raise Exception()` directo
- Commits: Conventional Commits (feat:, fix:, refactor:, ...)
- Tests: junto al archivo fuente como `test_archivo.py`

4. Patrones específicos y prohibiciones

# Patrones — crear un nuevo endpoint
1. Definir schemas Pydantic en `schemas/`
2. Crear el router en `api/routers/` (se registra solo si está en la carpeta)
3. Agregar tests en el mismo directorio

# Prohibiciones
- NO usar `type: ignore` sin comentario que lo justifique
- NO modificar archivos en `generated/` — son autogenerados
- NO commitear archivos `.env`

Jerarquía de archivos CLAUDE.md

Claude Code carga CLAUDE.md en varias ubicaciones, construyendo contexto acumulativo:

Ubicación Alcance ¿Se commitea?
~/.claude/CLAUDE.mdGlobal — tus preferencias personalesNo (personal)
./CLAUDE.md (raíz del proyecto)Proyecto — compartido con el equipoSí
./src/CLAUDE.md (subdirectorio)Módulo — se carga cuando Claude opera en esa carpetaSí

El contexto se construye de forma aditiva: global + proyecto + subdirectorio.

Global vs proyecto: Usá ~/.claude/CLAUDE.md solo para preferencias genuinamente personales ("respondeme en español", "respuestas concisas"). Toda decisión de equipo (idioma de commits, convenciones de testing) va en el CLAUDE.md del proyecto para que sea consistente y versionable. Evitá reglas globales que contradigan las del proyecto.

Tamaño recomendado: Apuntá a menos de 200 líneas por archivo. Los archivos largos consumen contexto y reducen la adherencia a las instrucciones. Si crece demasiado, parte del contenido debería vivir en skills o en reglas por ruta.

Reglas por ruta — .claude/rules/

Para proyectos grandes, organizá las instrucciones en múltiples archivos dentro de .claude/rules/. Cada uno puede limitarse a archivos específicos mediante frontmatter paths — solo se carga cuando Claude trabaja sobre archivos que coinciden:

---
paths:
  - "src/api/**/*.py"
---
# Reglas de desarrollo de API
- Todos los endpoints deben validar input
- Formato de error estándar: { error, message, code }

Las reglas sin paths se cargan al inicio de la sesión, como CLAUDE.md. Las que tienen paths reducen el ruido y ahorran tokens.

Auto Memory — Claude aprende solo

Auto Memory es un sistema paralelo a CLAUDE.md donde Claude escribe sus propias notas entre sesiones: comandos de build descubiertos, insights de debugging, convenciones observadas. Se cargan automáticamente al inicio de cada sesión (el índice MEMORY.md).

# Ver y gestionar la memoria de la sesión
/memory

# Pedirle que recuerde algo explícitamente
> Recordá que este proyecto usa pnpm, no npm

CLAUDE.md vs Auto Memory: CLAUDE.md es lo que vos escribís: reglas, arquitectura, convenciones. Auto Memory es lo que Claude aprende mientras trabaja: comandos que descubrió, patrones observados, bugs ya resueltos. Ambos se cargan en cada sesión y se complementan.

Importar archivos en CLAUDE.md

Con la sintaxis @ruta/archivo importás otros archivos directamente. El contenido se expande en contexto al inicio de la sesión, evitando duplicar información:

# CLAUDE.md
Consultá @README.md para el resumen y @pyproject.toml para los comandos.

# Preferencias personales (no se commitea)
@~/.claude/my-preferences.md
06

Custom Skills

¿Qué son las Skills?

Las skills son archivos Markdown (SKILL.md) con instrucciones detalladas y best practices para un tipo específico de tarea. Son "recetas" que Claude sigue cuando necesita hacer algo particular.

La diferencia es la que hay entre decirle a un dev "hacé un PDF" y darle un documento que explica exactamente qué librería usar, qué template seguir y cómo manejar fuentes y márgenes. Eso segundo es una skill.

CLAUDE.md vs SKILL.md — ¿por qué separarlos?

Técnicamente los dos son Markdown con instrucciones; lo que los separa es cuándo y a qué costo se cargan en contexto:

Aspecto CLAUDE.md SKILL.md
Cuándo se cargaSiempre, al inicio de cada sesiónBajo demanda, solo cuando la tarea lo requiere
Costo en tokensSe paga en cada promptSe paga solo cuando se usa
Contenido idealLo que todo dev necesita el día 1Instrucciones detalladas para una tarea concreta
AnalogíaEl onboarding generalEl manual que abrís solo cuando hacés esa tarea

El problema de meter todo en CLAUDE.md: Un archivo de 2000 líneas diluye todo. Las convenciones importantes se pierden entre instrucciones que no son relevantes el 95% del tiempo — y ni vos ni Claude las aprovechan bien.

Estructura de una Skill

Una skill es un directorio con, como mínimo, un SKILL.md. Su potencial real aparece cuando incluye templates, examples y helpers que Claude puede leer y ejecutar:

migrar-storage-a-db/
├── SKILL.md          # Instrucciones y proceso (obligatorio)
├── templates/        # Scaffolding real que Claude completa
│   └── media_storage_service.py
├── examples/         # Cómo debería verse el output terminado
│   └── output_service.py
└── helpers/          # Scripts que Claude ejecuta (verificación, validación)
    └── verify_migration.sh
  • Templates — el esqueleto con los imports, tipos y firmas correctos del proyecto. Sin template, Claude genera desde cero con su criterio; con template, arranca desde la estructura que definió tu equipo.
  • Examples — el resultado esperado. Especialmente útiles para output visual: Claude puede *ver* imágenes, así que una captura de referencia (grafica-ok.png) es infinitamente más precisa que "usá colores pastel y que se vea lindo".
  • Helpers — scripts ejecutables que automatizan verificación (por ejemplo, comparar checksums entre el archivo original y el migrado).

El potencial completo: Con templates + examples + helpers le das a Claude el esqueleto desde el que empieza, el estándar de cómo debería verse el resultado, y las herramientas para verificar su propio trabajo. Un dev sin eso arranca de cero; con eso, arranca sobre un setup que el equipo ya dejó armado.

Ejemplo de SKILL.md (recortado)

---
name: migrar-storage-a-db
description: Migra módulos que almacenan archivos en filesystem local a
  almacenamiento en base de datos (binario o referencias a object storage).
---

# Migrar Storage de Ficheros a Base de Datos

## Reglas de decisión
- Archivos < 1MB (thumbnails, avatars): almacenar como `bytea` en PostgreSQL.
- Archivos >= 1MB (fotos HD, videos): subir a object storage y guardar solo
  la URL + metadata en DB.
- NUNCA borrar los ficheros originales hasta verificar la migración.

## Proceso paso a paso
1. Crear la migration de la tabla `media_assets`.
2. Crear el servicio `MediaStorageService` con `migrate_file()` y `get_file()`.
3. Crear un script batch idempotente (skip por checksum) con log de progreso.
4. NO tocar los endpoints existentes hasta que el batch esté verificado.

## Verificación
- Comparar checksums entre original y migrado.
- Reporte final: total, migrados, skipped, errores.

## Prohibiciones
- NO borrar archivos originales en ningún paso.
- NO hacer la migración y el cambio de endpoints en el mismo PR.

Impacto: Sin skills, Claude improvisa desde conocimiento general. Con skills, sigue exactamente los patrones y procesos de tu proyecto. La consistencia del output mejora dramáticamente.

Argumentos e invocación

Las skills pueden recibir argumentos mediante $ARGUMENTS (o por posición: $0, $1, ...). Invocar /fix-issue 347 inyecta "347":

---
name: fix-issue
description: Fix a GitHub issue by number
disable-model-invocation: true
---
Investigá y corregí el issue de GitHub número $ARGUMENTS siguiendo los
estándares del proyecto. Escribí los tests necesarios y hacé commit.

Control de invocación

Campo Efecto Cuándo usarlo
disable-model-invocation: trueSolo el usuario invoca la skill; Claude no la activa soloSkills con efectos secundarios: /deploy, /commit
user-invocable: falseSolo Claude la invoca; no aparece en el menú /Conocimiento de fondo que Claude aplica automáticamente

Ejecutar en subagente aislado (context: fork)

Con context: fork en el frontmatter, la skill corre como prompt de un subagente en un contexto aislado, sin acceso al historial de la conversación. El resultado vuelve a la sesión principal:

---
name: deep-research
description: Research a topic thoroughly across the codebase
context: fork
agent: Explore
---
Investigá exhaustivamente "$ARGUMENTS": encontrá archivos relevantes con
Glob y Grep, analizá patrones, y resumí con referencias a archivo:línea.

Skills y comandos incluidos

Claude Code trae skills y comandos disponibles sin configuración:

Comando Qué hace
/batch <instrucción>Cambios a gran escala en paralelo: descompone el trabajo, lanza un subagente por unidad en un git worktree aislado, y cada uno abre su PR
/simplify [foco]Revisa archivos modificados buscando reutilización, calidad y eficiencia; aplica correcciones con agentes en paralelo
/debug [descripción]Habilita logging de debug y analiza los logs para identificar la causa del problema
/loop [intervalo] <prompt>Ejecuta un prompt repetidamente en un intervalo (monitorear un deploy, hacer polling de un estado)

Plugins y marketplaces: Además de las skills sueltas, Claude Code tiene un sistema de plugins: bundles de skills, comandos, subagentes y MCP servers que se instalan desde un *marketplace* (/plugin). Es la forma recomendada de distribuir conjuntos de herramientas dentro de un equipo u organización.

07

Subagentes y Orquestación

Los subagentes son asistentes especializados que Claude Code lanza para sub-tareas. Cada uno corre en su propia ventana de contexto, con system prompt propio, herramientas restringidas y, opcionalmente, un modelo distinto al de la sesión principal.

Ataca un problema concreto del trabajo agéntico: a medida que la conversación crece, el contexto se llena de resultados de exploración que "ensucian" la sesión. Con subagentes, esa exploración ocurre aislada y solo el resultado final vuelve al agente principal.

Subagentes integrados

Claude Code ya los usa automáticamente cuando el contexto lo amerita:

Subagente Modelo Herramientas Cuándo lo usa
ExploreRápido/económicoSolo lecturaBuscar o entender el codebase sin hacer cambios
PlanHereda principalSolo lecturaEn plan mode, para investigar antes de proponer
General-purposeHereda principalTodasTareas complejas de múltiples pasos (explorar + modificar)

Importante: Los subagentes no pueden generar otros subagentes. Solo el agente principal delega. Esto evita cadenas de recursión incontrolables.

Crear subagentes personalizados

Son archivos .md con frontmatter YAML en .claude/agents/ (proyecto) o ~/.claude/agents/ (usuario):

---
name: code-reviewer
description: Reviews code for quality and security. Use proactively after code changes.
model: sonnet
tools: Read, Grep, Glob
memory: project
---
Sos un code reviewer senior. Analizá el código y devolvé feedback específico
y accionable sobre calidad, seguridad y buenas prácticas. Priorizá problemas
reales sobre sugerencias cosméticas.

El campo description es crítico: Claude lo usa para decidir cuándo delegar automáticamente. Frases como "use proactively after code changes" hacen que lo invoque sin que se lo pidas.

Campos de frontmatter

Campo Requerido Descripción
nameSíIdentificador único (minúsculas con guiones)
descriptionSíCuándo Claude debe delegar
modelNoopus, sonnet, haiku, o ID completo. Por defecto hereda el modelo de la sesión
toolsNoLista blanca de herramientas. Si se omite, hereda todas
disallowedToolsNoLista negra: hereda todo excepto estas
permissionModeNodefault, acceptEdits, plan, bypassPermissions, etc.
memoryNouser, project o local — memoria persistente entre sesiones
skillsNoSkills a precargar en el subagente
mcpServersNoMCP servers disponibles solo para este subagente
maxTurnsNoLímite de turnos antes de detenerse

Configuración avanzada

Selección de modelo por tarea

Enrutá cada tipo de tarea al modelo más apropiado, balanceando costo, velocidad y calidad. Usá los alias (opus/sonnet/haiku) en vez de versiones fijas: cada alias apunta al modelo más nuevo de su familia, así tu config no queda desactualizada:

Alias Usar para
haikuExploración, búsqueda de archivos, preguntas simples — máxima velocidad y mínimo costo
sonnetLa mayoría de tareas de implementación, reviews, tests — balance ideal. Es el modelo por defecto en Claude Code, con ventana de contexto nativa de 1M tokens
opusAuditorías de seguridad, decisiones arquitectónicas, análisis complejos — máxima calidad

Restricción de herramientas

tools: Read, Grep, Glob            # lista blanca (más restrictivo)
disallowedTools: Write, Edit       # lista negra (más permisivo)

Si definís ambos, disallowedTools se aplica primero.

Memoria persistente entre sesiones

Alcance Ubicación Cuándo usarlo
project.claude/agent-memory/<name>/Conocimiento del proyecto, compartible vía git
user~/.claude/agent-memory/<name>/Aprendizajes aplicables en todos los proyectos
local.claude/agent-memory-local/<name>/Específico del proyecto, sin commitear

Invocar subagentes

# 1. Lenguaje natural (delegación automática si el description está bien escrito)
> Usá el subagente code-reviewer para revisar los cambios del branch feature/payments

# 2. @-mention (delegación garantizada)
> @code-reviewer revisá los cambios de autenticación que acabo de hacer

# 3. Sesión completa como subagente
claude --agent security-auditor

El slash command /agents abre una UI interactiva para crear, editar y eliminar subagentes sin tocar archivos, e incluso generarlos a partir de una descripción en lenguaje natural.

Ejemplos prácticos

Listos para agregar a .claude/agents/. Cada uno muestra una capacidad distinta:

code-reviewer — review automático post-cambios, solo lectura, con memoria de proyecto:

---
name: code-reviewer
description: Reviews code for quality, security and best practices. Use proactively after any code change.
model: sonnet
tools: Read, Grep, Glob
memory: project
---
Sos un code reviewer senior. Buscá bugs, seguridad, performance y violaciones
de patrones. Consultá tu memoria antes de empezar y actualizala al terminar
con patrones nuevos o issues recurrentes.

fast-explorer — investigación de bajo costo con el modelo más rápido:

---
name: fast-explorer
description: Quickly explores the codebase to answer questions about structure and patterns.
model: haiku
tools: Read, Grep, Glob, Bash
---
Respondé preguntas sobre la estructura del proyecto de forma rápida y concisa.
No modificás archivos.

security-auditor — auditoría con el modelo de máxima calidad, solo lectura por diseño:

---
name: security-auditor
description: Performs thorough security audits. Use when reviewing auth, data handling or external integrations.
model: opus
tools: Read, Grep, Glob
memory: project
---
Auditá el código buscando OWASP Top 10, manejo inseguro de credenciales,
problemas de auth e inyecciones. Explicá impacto y remediación de cada issue.

Patrón coordinador

Para tareas grandes con múltiples especialistas, un subagente coordinador orquesta a los demás. tools: Agent(...) define qué subagentes puede lanzar:

---
name: feature-coordinator
description: Coordinates feature implementation end-to-end.
model: sonnet
tools: Agent(fast-explorer, test-writer), Read, Bash
---
1. Delegá la investigación a fast-explorer.
2. Implementá los cambios vos mismo.
3. Delegá los tests a test-writer.
4. Corré el suite completo.

Recordá: Como los subagentes no generan otros subagentes, el patrón coordinador solo funciona cuando el coordinador corre como agente principal: claude --agent feature-coordinator.

El salto de productividad: Un equipo que define sus subagentes una vez obtiene un conjunto de "especialistas" reutilizables con @nombre: el code-reviewer que aprendió los patrones del proyecto, el security-auditor que recuerda las vulnerabilidades ya encontradas, el test-writer que sabe cómo escribe tests el equipo. Es conocimiento institucional empaquetado en agentes.

MCP Servers (Model Context Protocol)

¿Qué es MCP?

MCP es un protocolo abierto que conecta Claude Code con herramientas y servicios externos. A los MCP servers los pienso como "plugins" que le dan capacidades más allá del filesystem y bash:

  • Consultar bases de datos (PostgreSQL, SQLite).
  • Interactuar con APIs (GitHub, Linear, Jira, Slack).
  • Buscar en la web o en documentación específica.
  • Conectar con herramientas internas de tu empresa.

Configuración

Se configuran a nivel global o de proyecto:

// .claude/settings.json
{
  "mcpServers": {
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres",
               "postgresql://localhost:5432/midb"]
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "ghp_..." }
    }
  }
}

Tipos de transporte: Los MCP servers se comunican por stdio (proceso hijo, lo más común) o por SSE/HTTP (servers remotos o cloud). El formato de configuración difiere levemente entre ambos.

Servers populares

Server Qué hace
server-postgresExplorar schemas y hacer queries de lectura
server-githubIssues, PRs, buscar código, crear branches
server-filesystemAcceso controlado a directorios fuera del proyecto
server-sqliteInteracción con bases SQLite

Seguridad: Los MCP servers tienen acceso real a tus servicios. Usá env vars para tokens, nunca los hardcodees en el settings.json que se commitea. Limitá los servers al mínimo necesario y no des acceso a producción.

Flags de CLI importantes

# Prompt directo (no interactivo)

# Pipe de input
cat error.log | claude -p "analizá este log y decime qué pasó"

# Continuar la última conversación / reanudar una específica
claude --continue          # o -c
claude --resume <nombre-o-id>   # sin argumento: selector interactivo

# Modelo específico (preferí los alias)

# Output JSON (scripting)

# Profundidad de razonamiento
claude --effort high       # low | medium | high | max  (también /effort en sesión)

# Modo bare: sin CLAUDE.md, hooks, MCP ni auto memory
claude --bare -p "query"

# Límites para pipelines
claude -p "..." --max-budget-usd 2.00
claude -p "..." --max-turns 10

¿Qué es un turno?: Un turno es un ciclo completo del agente: recibe input → razona → ejecuta herramientas (pueden ser muchas) → devuelve respuesta. --max-turns 10 permite hasta 10 de esos ciclos. El mismo concepto aparece en maxTurns de los subagentes.

Modos de ejecución

  • Interactivo (default): REPL conversacional. Claude pide permisos, aprobás, iterás.
  • One-shot (-p): ejecuta un prompt y responde sin interactividad. Ideal para scripts.
  • Pipe: recibe input por stdin, combinable con -p, integrable en pipelines de shell.
  • Headless (CI/CD): sin interactividad ni confirmaciones. Ver módulo siguiente.
git diff main | claude -p "revisá este diff buscando bugs potenciales"

Sistema de Hooks

Los hooks son handlers que se ejecutan automáticamente en puntos del ciclo de vida de Claude Code, sin intervención humana: linting tras cada edición, bloqueo de comandos destructivos, notificaciones, logging de auditoría. Se configuran en la clave hooks del settings.json:

{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Write|Edit",
      "hooks": [{ "type": "command", "command": "ruff check --fix", "timeout": 30 }]
    }],
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{ "type": "command", "command": ".claude/hooks/block-rm.sh" }]
    }]
  }
}

Eventos principales

Evento Cuándo se activa ¿Puede bloquear?
PreToolUseAntes de ejecutar una herramientaSí — puede denegar
PostToolUseDespués de ejecutar exitosamenteSí — puede revertir
SessionStartAl iniciar o reanudar una sesiónNo
StopCuando Claude termina de responderSí — puede forzar más trabajo
NotificationCuando Claude pide permiso o queda idleNo
SubagentStart/StopAl iniciar/terminar un subagenteNo

Tipos de hook: command (script de shell; exit code 2 bloquea), http (POST a una URL), prompt (evalúa con un prompt a Claude), agent (lanza un subagente para decidir). Usá /hooks para ver los configurados.

Git Worktrees — aislamiento real para trabajo paralelo

La forma recomendada para trabajo paralelo con múltiples instancias no es abrir terminales en el mismo directorio, sino usar git worktrees: cada instancia trabaja en su propio directorio y su propia rama, sin conflictos.

# Crear un worktree aislado e iniciar Claude en él
claude --worktree feature-auth      # alias: -w

# Dos instancias completamente aisladas
claude -w feature-payments          # Terminal 1
claude -w bugfix-login              # Terminal 2

# Sin nombre: genera uno automáticamente
claude -w

Los worktrees se ramifican desde origin/HEAD. Al salir: si no hubo cambios, el worktree se elimina; si hubo, Claude pregunta si querés mantenerlo.

Archivos .env: Los worktrees son copias limpias — no incluyen gitignored como .env. Para copiarlos automáticamente, creá un .worktreeinclude en la raíz (misma sintaxis que .gitignore).

Seguridad y buenas prácticas

  • Commiteá .claude/settings.json con los permisos del equipo; settings.local.json para overrides personales.
  • Nunca auto-aprobar git push — requerí confirmación humana.
  • Revisá diffs antes de commitear — git diff después de que Claude trabaje. Confiá pero verificá.
  • Usá branches (o worktrees) para el trabajo de Claude, y revisá el PR.
  • Limitá los MCP servers al mínimo — no des acceso a producción.
  • API keys rotadas y con scopes — nunca uses tu key de admin para CI/CD.

Gestión de costos

  • /cost durante la sesión para ver el gasto.
  • /compact para reducir tokens en conversaciones largas.
  • Prompts específicos > prompts vagos: un prompt vago genera idas y vueltas que consumen tokens.
  • Modelos apropiados: haiku para exploración, sonnet para tareas rutinarias, opus cuando necesitás máxima calidad de razonamiento.
